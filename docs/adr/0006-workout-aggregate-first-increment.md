# ADR 0006: Workout aggregate, first increment — a flattened aggregate, not WorkoutSession rebuilt in full

- Status: accepted
- Date: 2026-07-29

## Context

Sprint 2, Step 2 asked for a standalone `Workout` aggregate: a four-state
lifecycle (`PLANNED`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`), planned/
started/completed/cancelled directly by name, `WorkoutName`/`WorkoutGoal`/
`WorkoutNotes`/`WorkoutDuration`/`WorkoutDate` value objects, and exactly
four events (`WorkoutPlanned`/`WorkoutStarted`/`WorkoutCompleted`/
`WorkoutCancelled`).

The Domain Model & Decision Engine Bible's closest concept is not one
aggregate but three, layered (Section 4.6–4.7): `WorkoutTemplate` (a
reusable, dateless pattern) instantiated into a `WorkoutPlan` (dates, phase,
a specific user, generated by the Plan Generator), which in turn generates
many `WorkoutSession`s (one calendar-day instance each, Section 4.7, Table
10) — with a five-state lifecycle (Scheduled -> InProgress -> Completed /
Skipped -> Reviewed -> Archived, Section 7.1, Table 30) that differs from
this increment's four states in two ways: `Scheduled`/`Reviewed`/`Archived`
aren't modeled, and the Bible has no user-initiated "Cancelled" at all — a
session that never starts becomes `Skipped` automatically once its date
passes, a time-driven transition this increment has no scheduler for.

Building the full three-aggregate hierarchy now, to make this increment's
`Workout` a literal `WorkoutSession`, would mean inventing `WorkoutTemplate`
and `WorkoutPlan` (and the Plan Generator that produces them) speculatively
ahead of any task asking for them. The task's own scope is explicit and
narrower than that. This is the same shape of decision ADR 0005 already made
for `UserProfile` vs. the standalone `Profile` aggregate, and it affects the
same kind of future work — the Exercise aggregate (next) and any eventual
`WorkoutPlan`/`WorkoutTemplate` aggregate will need to reconcile with
whatever shape `Workout` has today — so it gets the same documentation
treatment.

## Decision

`app/domain/workout/` implements a single, standalone `Workout` aggregate:

- No `WorkoutPlan` reference (no `plan_id`) — a `Workout` is planned
  directly, not generated from an owning Plan. The Bible's Plan Generator
  and the periodization/progression logic it depends on are out of scope.
- No `ExerciseSet` relationship, no `tier_selected`, no `RPE`, no
  `pain_flag` — logging individual sets and the safety-escalation trigger
  those carry (Table 10, "Business rules": a `pain_flag` above threshold
  triggers Safety Escalation mid-session) both need aggregates
  (`Exercise`, `SafetyFlag`/`EscalationCase`) that don't exist yet.
- Four states, not five, and `Cancelled` instead of `Skipped`/`Reviewed`/
  `Archived`: `Cancelled` is an explicit user action available from
  `Planned` or `InProgress`, matching the task's own named invariants
  ("cannot cancel after completion"). A `Skipped`-equivalent (a workout
  whose date passed with nothing logged) is a time-driven transition that
  needs a scheduler evaluating "has today passed" against every `Planned`
  workout — this increment has no such process, so it isn't modeled as a
  state at all. `Reviewed`/`Archived` are Progress Review integration
  points (Section 6.8) that don't exist yet either.
- `WorkoutDuration` is a caller-supplied value at `complete()`, not derived
  from `started_at`/`completed_at` — see that value object's own
  docstring for why (a logged duration legitimately differs from raw
  elapsed wall-clock time, and a manually logged past workout, Product
  Bible MVP tier, may have no live start/stop at all).
- `WorkoutGoal` is a short, free-text label, not a reference to the Bible's
  `Goal` aggregate (Section 4.4) — same reasoning as ADR 0005's `AuthMethod`
  decision: inventing a cross-aggregate reference before a documented need
  for it exists would be premature coupling, not flexibility.

## Consequences

Reconciling `Workout` with the Bible's full `WorkoutTemplate` ->
`WorkoutPlan` -> `WorkoutSession` hierarchy is a real, future migration —
most plausibly, `Workout` becomes (or is absorbed into) `WorkoutSession`
once a `WorkoutPlan` aggregate exists to generate it from, gaining
`plan_id`, the `Scheduled`/`Skipped`/`Reviewed`/`Archived` states, and an
`ExerciseSet` relationship at that point. Until then, every `Workout` is
user- or (later) directly-AI-suggested, never Plan-generated.

The state-name mismatch (`Cancelled` here vs. no such state in the Bible's
`WorkoutSession`) is an accepted, documented rough edge, the same class of
decision as ADR 0005's `UserContext` naming note — not a silent
reinterpretation of the Bible. If a future increment adds real Plan-driven
scheduling and needs a genuine `Skipped` (time elapsed, nothing logged)
distinct from `Cancelled` (explicit user action), both can coexist as
separate states; nothing here forecloses that.

No aggregate beyond `User` and `Workout` yet references or is referenced by
`Workout` — the `Workout.update_goal`/`update_notes` no-event pattern and
the four-event scope both follow ADR 0005's already-established "add an
event only once a real subscriber needs it" discipline, not a new decision
being introduced here.
